# Implement frontend UI

Turn the requested frontend change into working interface behavior. Locate Atlas through the shared-resource links below; keep the library distinct from the consuming project. Start with the user's request, governing project instructions, relevant design documents and affected implementation.

## Establish the bounded change

Inspect the existing stack, reusable components/tokens, state owners and available development/check commands. Preserve the project's visual direction, architecture, content and existing work. A small, clear task can proceed without design.md; do not automatically create a design document, choose another theme, replace the stack or invoke preparation/review.

Identify the user action and observable result, affected routes/components, and applicable empty, invalid, pending or recovery states. Resolve consequential missing behavior from nearby conventions and supplied evidence. Ask only when a missing decision blocks correct implementation. Distinguish browser-local behavior, simulation and actual service capabilities; a UI control cannot establish an unsupported backend guarantee.

## Select guidance for an actual decision

Use the project's self-contained rules first. Open [the knowledge index](../../knowledge/README.md) only when an unresolved decision needs Atlas guidance, then select relevant sections and their credits. Do not load the catalog, every theme, upstream skill bundles, research ledger or historical trials for a routine implementation.

Route hierarchy, layout, writing, typography or component mapping to general UI/UX; implicated semantics, keyboard/focus, reflow, input or appearance to accessibility/responsive guidance. Stateful edits may need state/recovery or forms/navigation; remote effects may need uncertain outcomes. Agent Experience applies when the product actually exposes agent work. Read the selected theme's effects or motion rules only when those choices are relevant and unresolved. For a requested or unresolved visual treatment, use the knowledge index's composition route and only the selected style rules; do not browse all families. Preserve the project's scope, theme overrides and opaque/preference fallbacks. Resolve needed guidance into the implementation or existing project handoff so later edits do not repeat the survey.

Use compatible craft guidance such as better-ui only when relevant and available. Explicit user choices and governing project design/accessibility rules take precedence over generic polish values; do not import another skill's fixed motion, shape or effect values when they conflict. Keep any additional guidance within this task rather than automatically launching a second review or loading every domain.

## Implement the task and its states

Reuse established components, semantic tokens and variants before adding competing abstractions. Follow the project's component ownership and map the requested role to its actual control, content and state. Prefer native semantics where they fit; keep names, input instructions, focus movement and feedback useful through the affected task. Check real content and long labels, rather than judging an isolated idealized specimen.

Keep state transitions and displayed evidence consistent with their owner. Preserve relevant user input and context through interruption or recovery. Choose styling and motion within the governing design; honor the project's appearance, reduced-motion and fallback contracts. Add dependencies, persistence, service integration or broader refactors only when the requested behavior needs them.

## Verify the changed experience

Run the relevant existing checks, then exercise the affected user path in the rendered interface when browser access is available. Verify useful outcomes and relevant alternate states, keyboard behavior and narrow layout. Include appearance, motion, reload, navigation or service checks when the change implicates them. Choose focused checks proportional to the change; avoid an automatic full-site audit or tests that merely repeat implementation details.

Fix demonstrated regressions and repeat the affected checks. Record the actual commands, interaction/context and observed results. Source inspection, automated assertions, visual inspection, assistive-technology checks and real-service evidence remain distinct. If a required tool or service is unavailable, state the remaining verification limit instead of claiming a pass.

## Deliver and preserve provenance

Report what changed, why, meaningful checks and material remaining limits. Preserve project/theme/asset credits. When copying code, assets or substantial covered adaptations, check that artifact's permission and carry its required notices; unresolved rights do not become permission. This original Atlas workflow's credited methods and retained licenses are recorded in [implementation workflow provenance](../../references/skill-adaptations.md#2026-10-20-implementation-workflow). That record and full notices are conditional provenance/distribution material, not routine implementation reads.
