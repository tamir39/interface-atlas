# Implement frontend UI

Turn the requested frontend change into working behavior using the project's rules and affected source. Locate Atlas through the links below; keep it distinct from the consuming project.

## Establish the bounded change

Find affected files by name or symbol, then follow relevant imports and governing document headings. Keep content searches within those files and return bounded matches/ranges; if output truncates, narrow it before continuing. Expand to a whole README or wider tree only for a named missing task fact. Inspect the stack, reusable components/tokens, state owners and check commands needed for this change. Preserve design direction, architecture, content and existing work. A clear bounded task needs no new design.md, theme, stack or preparation/review stage.

Identify the action, observable result, affected routes/components and applicable alternate states. Resolve missing behavior from nearby conventions and evidence; ask only when a decision blocks correct implementation. Distinguish local behavior, simulation and real service capabilities. A control cannot supply an unsupported backend guarantee.

## Select guidance for an actual decision

Use the project's resolved rules first. For a remaining question, read its known section directly or use [the knowledge index](../../knowledge/README.md) to locate it. Read only relevant sections and necessary dependencies, then stop. Reuse this task's conclusions/read records instead of reopening the index, whole chapters or supporting sources. Routine implementation needs no catalog, upstream bundle, research ledger or historical trial.

Theme effects/motion, style composition and Agent Experience are conditional on actual task decisions. Do not add persistence, agent or remote-action contracts to unrelated features. Resolve accepted guidance into code or the existing handoff so later edits need no repeated survey.

Use relevant craft guidance such as better-ui when available. Apply its useful sections within project/design/accessibility rules; fixed motion, shape or effect preferences do not override those rules. Do not load the entire companion skill family or launch another workflow merely because one craft concern applies.

For an unresolved component/effect, read an identified recipe directly or use [pattern discovery](../../catalog/patterns.json). Read selected rules/credits; preserve governing tokens, components and task behavior. Resolved tasks skip discovery. A preview requires no new stack, package or service.

## Implement the task and its states

Reuse components, semantic tokens and variants before adding abstractions. Follow component ownership and use native semantics where they fit. Keep names, instructions, focus and feedback useful throughout the affected task; check real content and long labels.

Keep transitions and displayed evidence consistent with their owner. Preserve relevant input/context through interruption and recovery. Honor appearance, reduced-motion and fallback contracts. Add dependencies, persistence, services or broader refactors only when requested behavior needs them.

## Verify the changed experience

Run relevant existing checks and exercise the affected path when browser access is available: useful outcomes, applicable alternate states, keyboard and narrow layout. Include appearance, motion, reload, navigation or services when implicated. Inspect rendered feedback with nearby fixed/sticky controls if they can overlap; overflow measurements alone do not detect occlusion. Keep checks proportional to the change, not a full-site audit or implementation-mirroring tests.

Fix demonstrated regressions and repeat affected checks. Record commands, context and observations. Distinguish source, assertions, pixels, assistive-technology and service evidence. State unavailable verification instead of claiming a pass; summarize results rather than dumping nested raw evidence.

Report the change, purpose, checks and material limits. Preserve project/theme/asset credits; use concise credits from selected guidance.
