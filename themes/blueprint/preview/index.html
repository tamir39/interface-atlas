Purpose & boundaries

01 / Input

Project brief

Start with the project you are actually building.

The brief describes who the interface serves, what those people need to do, and which constraints matter. Include the project type, intended platforms, languages, existing brand decisions, and the most important user journeys.

Receives
Project context and human priorities
Provides
Context and constraints for Design preparation
Boundary
An input, not an approval or a generated design

Illustrative example: a bilingual developer portfolio that needs clear case studies and accessible navigation.

02 / Library

Theme catalog

Choose knowledge that fits the project's purpose.

Use a theme's summary to shortlist a visual direction. Read its design rules, then load only the effects, motion, and shared knowledge the project needs. Keep the source creator and revision attached to the decisions you take forward.

Receives
Theme entries and source records
Provides
Selected, credited design knowledge for Design preparation
Boundary
A knowledge library, not a bundle to load for every task

Illustrative example: compare Blueprint's technical language with Editorial's narrative reading rhythm.

03 / Concept

Design preparation

Turn the selected direction into concrete project decisions.

This conceptual step combines the brief with selected knowledge. It specifies type, hierarchy, layout, color roles, component states, responsive behavior, and interaction flows. Document adaptations explicitly and keep unresolved choices visible for review.

Receives
Project brief and selected Theme catalog knowledge
Provides
Design decisions for the Project design.md
Boundary
A described preparation step; no agent runs in this preview

Illustrative example: choose Blueprint's geometry while preserving comfortable body typography for case-study reading.

04 / Artifact

Project design.md

Give implementation a document it can use on its own.

The project document records the chosen direction and the rules necessary to build it. Include the selected tokens, key layouts, user flows, motion constraints, accessibility requirements, validation expectations, and source credits. Distinguish retained rules from project adaptations.

Receives
Explicit decisions from Design preparation
Provides
Decisions and open questions for Human review
Boundary
An illustrative artifact in this map; no file is created here

Illustrative example: a project-specific document with source credits that implementation can consult without loading the full Atlas.

05 / Decision

Human review

Make the next decision visible to the person responsible.

Review whether the document fits the brief, explains its adaptations, and gives enough guidance for implementation. Identify missing evidence and unresolved choices. A reviewed design still needs to be tested in the actual project.

Receives
The Project design.md and its open questions
Provides
A next decision for the real project workflow
Boundary
No approval is recorded and no external action is taken

Illustrative example: revise the reading measure before accepting the project's design direction.
