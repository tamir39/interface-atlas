## Atlas contribution versus proposed commerce model

Atlas supplied enough explicit visual language to produce a self-contained palette/type/layout/media/motion draft without reopening all themes. The catalog and three READMEs narrowed selection; Gallery's design and sources made color pairing, accurate versus cropped imagery, recovery, credit, font, and licensing boundaries unusually clear. The template prompted state ownership, persistence, recovery, and validation sections. No optional knowledge file was necessary: the product exposes guest shopping, not agent work.

The storefront's product model mostly comes from agent judgment prompted by the brief: variant selection, cart schema, quote revisions, changed-price review, quantity rules, line reconciliation, checkout idempotency/status expectations, and unknown-outcome handling. These are explicit proposals, not Atlas's existing commerce patterns. A plausible document can therefore mask a reusable-knowledge gap unless provenance labels are retained. The draft does retain them.

The handoff section specifies capabilities that need agreement. It does not establish that a backend implements them, that a provider supports them, or that a purchase can currently succeed. Document completeness cannot close this evidence gap.

## Missing reusable knowledge and skill roadmap input

1. **Commerce state and authority knowledge — highest priority.** Add framework-independent distinctions among catalog observation, local intent, authoritative quote, availability versus reservation, hosted session, payment, and accepted order. Include change/review/reconciliation matrices, unknown results, retry limits, and late-response examples. Keep specific endpoints/provider details in the project. This gap is not repaired by adding colors or a component specimen.
2. **Persistence and conflict knowledge — high priority.** A reusable decision guide should cover versioned schema validation, unavailable/quota/corrupt storage, durability wording, reload restoration, cross-tab conflicts, sensitive fields, and independent local/backend revisions. The trial currently invents these safeguards through agent judgment.
3. **Transactional handoff and recovery knowledge — high priority.** Reusable capability checklist and outcome state matrix for checkout creation, lost acknowledgments, idempotency, safe attempt references, redirects, return-status lookup, expiry/cancellation, and completion reconciliation. Distinguish business contract questions from client error treatment; never present the checklist as supplied service behavior.
4. **Catalog/media intake — medium priority.** Gallery already provides useful crop/alt/loading/provenance rules. Add a reusable project intake schema for SKU/variant media mapping, exact object fidelity, commercial-data scope/freshness, photographer/license/credit, missing-image policy, source dimensions, and derivative budgets. The actual rights and assets remain project responsibilities.
5. **Evidence-led storefront review adapter — after knowledge exists.** Extend the existing prepare workflow conditionally for commerce briefs: request/map essential contracts, cite which rules were inherited, identify unsupported requirements, generate a contract-gated draft, and check recovery coverage. Keep theme selection separate from claiming a working commerce flow. Do not implement this skill based solely on one successful draft.

The absent API/provider/tax/reservation decisions, real catalog/assets, and package rights are **project inputs**, not promises Atlas can fill. Build guidance that exposes these absences; do not add fictional integrations. No new skill, theme, template, or knowledge document is implemented in this trial.
