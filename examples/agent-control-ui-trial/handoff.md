# Harbor Desk UI — bounded interaction and design handoff

Revision `0.1.0`, 2026-11-05. This is an original static simulation derived from the [historical interaction contract](../agent-control-evaluation/interaction-contract.md) and fictional brief. The original archive remains a document exercise. Its unspecified service inputs are not implemented capabilities. The [credits](credits.md) distinguish installed published guidance from the local Agent Experience draft.

## Scope and design

The fictional assistant drafts room-change notices for `RUN-HARBOR-07`; each of `REQ-201`, `REQ-202` and `REQ-203` needs a separate decision. No bulk authorization, confidence score, participant result, progress percentage or real delivery is supplied. A global notice identifies the simulation before the workspace. Operator actions and explicitly labelled local fixture controls occupy different regions.

Precision `0.1.0-draft` supplies selected Atlas palette roles, flat page/panel/supporting layers, 4px corners, 4/8/12/16/24/32px spacing, readable metadata, system-font fallbacks and a 3px focus outline with 3px offset. The implementation is original HTML/CSS/JavaScript, without copying a theme preview or upstream code. The desktop composition uses a persistent request rail and inline decision, with evidence beneath the action; steering and cancellation are distinct working regions. At 740px the list precedes detail, at 440px requests stack. No fixed overlay can cover task content. Details open natively, and only 110ms color/border feedback is used. Reduced motion removes transitions. No scale-on-press is selected: stable operation targets follow this theme’s motion contract. Forced-colors retains explicit structural, selected and focus boundaries. These are implementation choices; rendered checks and exclusions belong in the independent evaluation.

## Inspect, revise and decide

Inspecting a request preserves the active filter and selects a stable request ID, then focuses the request heading. Comparison includes immutable proposal/version, expected session revision, target session/time, current/proposed room, complete notice, frozen recipient snapshot, authorized source links, distinct source types/times, and the exact complete-proposal consequence beside the publish control. The generated explanation is labelled rationale, never corroboration. Snapshots supply no live recipient count.

The currently inspected copy stays separate from current fixture evidence. Replacing a proposal preserves the old comparison and typed text, gates that old decision and offers deliberate review of the current version. Permission withdrawal removes recipient detail from the rendered UI, retains permitted fictional references and working text, and gates actions. This is simulated display authorization; the source code contains fictional fixtures and is not a secure access-control mechanism.

**Edit draft** opens a working notice copy naming its base version and focuses the field. **Save revised local draft** deliberately retains a new immutable proposal on this browser; it sends no publish command and requires a new review. A stale base, unavailable permission, unresolved publish action or failed retention gates saving while preserving typed text. A deliberate failed save focuses its persistent error without marking valid text invalid. **Decline request** is discoverable but gated: the supplied fixture has no verified decline-resolution/recovery contract. No decline capability is invented.

## Publish, uncertainty and observation

Before local dispatch, the prototype reserves an `ACT-n` identity and writes/reads back its permitted recovery record. Only acknowledged retention crosses the local dispatch boundary. This prepared record is not delivery evidence. A second write records requested state; if it fails, the visible state is memory-only and a retained prepared record restores as unknown. The synchronous action guard dispatches once on repeated activation within this page. No cross-tab, device, backend or downstream duplicate guarantee is claimed.

| Observation | Operator wording and gate |
| --- | --- |
| Local dispatch | Requested; delivery unconfirmed. Original immutable action snapshot remains visible. |
| Matching acceptance fixture | Accepted; publication pending. No effect inferred. |
| Matching confirmed effect | Published, with effect reference, proposal/version and observation step. |
| Reply lost / inconclusive lookup | Publication outcome unknown. Original action remains; a fresh overlapping publish is unavailable. |
| Lookup denied after known effect | Current refresh limitation appears while historical confirmed effect remains established. |
| Attention resolved elsewhere | Attention closes; no published effect is inferred. |

**Check status** is command-specific lookup for the selected retained publish identity. The fixture controls stage a matching confirmed, denied or inconclusive result; the operator explicitly observes it. There is no polling, retry, automatic reconnect reconciliation or fresh overlapping publish. Other requests remain usable. Replacement versions cannot bypass the original unresolved action. Offline changes observation availability/freshness and gates new local commands; it never converts execution truth to success/failure or erases effect history. Reconnection performs no automatic action.

The four visible dimensions are execution observation, human attention, publish command and connection freshness. The deterministic fixture clock starts at `08:45:00 UTC`; steps record manual evidence advances, not real service time or elapsed performance. A completed attention item establishes neither delivery nor effect.

## Correction and cancellation

Corrections explicitly name remaining unsent request IDs. Editable memory-only text, retained submitted `COR-n / v1` snapshot/scope, receipt acknowledgement and applicability evidence are distinct. Later typing survives acknowledgement. A later lost reply cannot withdraw known receipt acknowledgement; it supplies no application evidence, so applicability remains unconfirmed and the known receipt stays retained. Unknown/sending/acknowledged corrections gate another submission only where scope overlaps. A supported non-overlapping remaining request stays available. A fixture application record explicitly names the later proposal revisions that used that correction; subject-matching text is insufficient. No training, lasting preference, recall or retrospective change is implied.

Cancellation is one best-effort `CAN-1` command for the frozen remaining scope. Requested observation, receipt acknowledgement, task-record closure and lost-reply history are retained separately. Execution observations remain visible alongside them. A lost cancellation reply leaves its command outcome unknown, without failure/stop wording; duplicate cancellation is gated because this fixture supplies neither command-specific lookup nor a duplicate-safe repeat policy. Refreshing publish/run evidence cannot establish cancellation receipt. A late matching publish-effect fixture can establish publication after task-record closure, preserving the cancellation history. There is no stopped/undone/rolled-back state or control.

## Focus, text and announcements

The request list’s deliberate inspection focuses the detail heading. **Back to requests** focuses the originating inspection button; when the filter hides it, focus goes to the filter with an explanation. Editing focuses the text field; deliberate save/return focuses the comparison heading. Leaving a dirty notice editor pauses in an inline keep/discard region and initially focuses **Keep editing**. Keep/Escape restores the editor; discard restores the base and continues the requested navigation. If a deliberate save succeeds while that choice is open, it cancels the obsolete pending navigation, closes the choice and stays at the revised comparison. A failed save preserves the choice and working text. No modal overlay or focus trap is needed. Correction text remains available in its separate global editor as requests change; its explicit discard action affects only unsent edits.

Background fixture changes update stable elements without moving focus or replacing local textarea contents. A concise persistent polite status region lies outside the decision/editor containers; it announces material outcomes, not every keystroke. Long notice text wraps; identifiers and action text do not depend on hover. Native controls, headings, labels, details and links provide keyboard routes. Screen-reader cadence and full conformance still require dedicated evaluation.

## Exact retention boundary

Local storage key: `harbor-desk-ui-trial-v1`, schema `1`, current browser/origin only, until explicit reset or browser data removal. The record retains only three known fictional request identities and definitions; current immutable saved proposal text/version; permitted fake segment references; last-observed attention, authority and effect records; original action identity, exact submitted snapshot, command observation and check result; submitted correction text/scope/applicability; cancellation identity/scope and separate command observations; appearance, selection, filter and fixture step. Input is treated as text, never HTML. Only fictional text should be entered. A strict bounded validator rejects corrupt/unknown identities and reconstructs known fields; unknown properties are not imported.

**Unsubmitted editable notice/correction text is memory-only.** This is explained beside each editor before a potential reload. Native `beforeunload` is supplementary, browser-dependent protection while text is dirty, not a recovery guarantee. In-app dirty notice navigation requires keep/discard. Deliberately saving a local draft or submitting a correction retains that snapshot, as stated at the action. Acknowledgement never clears newer typing. Reload restores actually retained snapshots and observations, not unsent editor text or a real service result. Unresolved publish actions require explicit lookup; prepared records become unknown rather than being resent.

Write/read-back failures visibly revoke claims that newer state was retained and gate new dispatch. Corrupt/unreadable prior history locks publish; it never silently discards unknown actions then offers a recovered fresh publish. The deliberate reset clears only this fictional local trial record and explains that it does not cancel or reverse work. File-URL storage behavior, private browsing, quotas and browser data removal can defeat retention. This is no production durability, authorization or multi-tab concurrency design.

## Remaining production inputs

No real service, endpoint, auth, authoritative clock, safe retry/ordering, service-generated action reservation, history retention/lookup authorization/expiry, protected-data storage policy, correction lookup, decline outcome, cancellation lookup or stopped-execution guarantee exists. Each needs an owned service/product contract and end-to-end evidence before a production promise. The interface alone supplies none of these. Independent browser checks exercise this static trial only; source assertions and pixels do not establish operator comprehension or real assistive-technology/service behavior.
