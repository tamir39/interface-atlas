# Harbor Desk — fictional operations desk brief

Prepared 2026-10-27 for a document exercise. No real users, service, source records, permissions or rendered interface are supplied. This is not a request to build a product.

A venue team uses an assistant to draft notices about session room changes. Operators inspect the changed room/session information, the proposed text and affected recipient segment, then decide whether to publish the proposal, revise its draft or decline it. Several sessions can need attention at once. Operators must also be able to understand which corrections affected remaining drafting work and what happened while they were away. The interface should preserve the team's existing visual system; theme selection is outside this exercise.

Use these **fictional service facts**, solely for this trial:

- Every run, decision request and proposal has a distinct identifier. Each request identifies an immutable proposal version and expected session-record revision. The service validates the current proposal/session revision and the operator's current permission before accepting a publish decision. Two authorized operators may inspect the same request; only a current unresolved request can accept a decision. The service can return a current snapshot identifying a resolved, superseded or expired request.
- Publishing changes an externally visible notice. An accepted decision is not completion of publishing. A service-generated action identifier can be retained before dispatch and queried after reload. The service exposes accepted, confirmed, rejected and unknown action outcomes with proposal/effect references; history retention and lookup authorization still need a project policy. A missing result alone does not establish that nothing was published.
- Corrections may change remaining unsent drafts only. A correction is assigned an identity/version; the service can acknowledge receipt separately from reporting which later draft revisions used it. It cannot recall an already published notice. A reply or later event can be lost, and an earlier draft can finish while a correction is pending.
- A cancellation facility can acknowledge a request and close its task record on a best-effort basis. It does not guarantee that underlying work stopped or that no later notice can appear. There is no supported recall/rollback capability in this fixture.
- Evidence includes a session-change record, an attendee-segment snapshot and a generated explanation. These are different source types and can have different observation times. One operator may later lose access to a recipient record. No model-confidence metric or learned-personalization behavior is supplied.
- A notification can be hidden locally. This does not resolve the service's decision request. Requests can expire or be resolved elsewhere while their details are open. The fixture supplies no bulk-approval operation.

Required journeys: understand delegation scope; scan and inspect a pending decision; compare a proposal with its source information; edit a draft or decline a request; dismiss a notification and later return; submit a correction during work; handle another operator resolving the inspected request; leave and recover an unresolved publish action; understand cancellation and any later effect evidence. Explain consequential choices without moving focus during background updates. No chat layout, framework, endpoint, retry guarantee or numeric approval tier is requested.

Prepare only a concise interaction contract. Resolve the operator-facing contents, action states, ownership boundaries, recovery/enablement rules and intended focus/announcement behavior. Distinguish supplied fictional facts, new project decisions and remaining service/product inputs. Include useful future validation but claim no executed UI, service, accessibility or user-study result.
