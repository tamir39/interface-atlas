## R1 — Medium: define how late successful checkout observations merge with newer evidence

**Reason and task impact.** Checkout recovery can receive more than one observation for the same stable action. The draft identifies the action and preserves evidence when a lookup fails, but does not define how an older successful response, or two contradictory successful responses, affect an already known state. Identity matching alone does not establish recency. A later-arriving pending observation could hide a known ready session and leave the guest unable to resume checkout through the intended recovery path.

**Exact locations.** In **Hosted checkout handoff and unknown outcomes**:

- Paragraph beginning “The commerce owner must contract service-enforced duplicate handling” lists status lookup and terminal evidence, but no service ordering/version contract or local conflict policy.
- Paragraph beginning “While preparing, guard duplicate activation” qualifies navigation by active request and cart revision, but does not qualify updates against newer evidence for the same action and revision.
- Paragraph beginning “After a proposed 12-second local wait” permits re-entry/reconnect and manual status checks. “If lookup fails, preserve the earlier evidence and label it stale” settles failed refreshes only.
- Paragraph beginning “Confirmed session creation permits Resume checkout” defines available actions for individual observations without a rule for merging observations.

**Concrete trigger.** A session-creation response and a status lookup overlap for action A and unchanged cart revision C. The newer service observation establishes that the session exists and provides a verified URL. A successful earlier lookup, describing A as still pending, arrives afterward. Alternatively, two lookups overlap around re-entry. Both identify A and C; all current identity guards therefore pass. The document does not say whether to retain the ready state, replace it with pending, or expose a contradiction when service ordering is unavailable.

**Counterevidence considered.** Stable action identity, independent transport-attempt identities, unchanged-payload restrictions, preservation after lookup failure, terminal-evidence requirements, and backend launch gates are substantial safeguards. They prevent several identity and retry errors. They do not define the local reduction of late successful observations. The availability rule elsewhere explicitly mentions request generation, showing that the design already distinguishes identity from freshness in another flow. This finding does not assume that a service provides sequence numbers or that an earlier quote necessarily becomes invalid when another quote exists.

**Bounded correction.** Add one recovery-evidence rule: retain the observation history for each stable action; qualify observations using contracted service identity and ordering; prevent older progress from replacing newer established state. When reliable ordering is absent and observations conflict, preserve confirmed evidence, expose the inconsistency, and seek authoritative reconciliation while keeping unsafe new actions gated. Specify how a late creation reply and a concurrent lookup merge. Add any required service version/finality fields to the commerce-owner gate. Do not use arrival order or browser timestamps as service truth. Apply an equivalent explicit policy to overlapping quote refreshes for the same cart revision if those are permitted.

**Evidence and basis.** This is an Atlas state/recovery recommendation applied to the brief's truthful unknown-checkout recovery requirement, rather than an asserted WCAG violation. The frozen review profile's **Observations or attempts may arrive late** trace and `knowledge/uncertain-outcomes.md`, **Cancellation and stale evidence**, distinguish matching identity from documented ordering and require contradiction handling. No runtime response ordering was observed.

## R2 — Medium: make the destructive saved-cart reset participate in a non-reused writer boundary

**Reason and task impact.** The draft proposes an explicit reset after storage-read trouble but does not say how that reset retires the pre-reset store identity or preserves a non-reused revision. Without that rule, an implementation can clear/recreate the record and allow an old tab or queued save whose base revision happens to match the recreated record to overwrite the newly chosen cart. The requirement to preserve same-browser intent makes this a material local recovery decision.

**Exact location.** **Cart ownership and durable recovery**, the paragraph beginning “Startup distinguishes loading,” specifically: “Start a new saved cart” is an explicit destructive reset and “must successfully complete before persistence is restored.” The ordinary save transaction is specified in the preceding paragraph; the following conflict paragraph specifies a reviewed-revision check for replacement. The reset paragraph supplies neither a retained monotonic revision nor an equivalent generation/writer-retirement rule.

**Concrete trigger.** Tab A holds a pre-reset draft and expected revision. Tab B encounters a quarantined record, explicitly chooses the new saved-cart reset, and successfully creates the replacement state. If reset deletes/recreates the record or restarts its counter, a subsequent save from A can encounter a matching revision and pass the ordinary comparison. An older queued completion can also arrive after the reset unless the acknowledgement boundary checks the retired identity. This is a permitted implementation ambiguity, not a claim that the draft requires counter reuse.

**Counterevidence considered.** Immutable serialized saves, expected-revision comparison inside a transaction, acknowledgement of only the saved snapshot, blocked writes during conflicts, advisory-only broadcasts, and rechecking replacement revisions are all useful safeguards. A strictly monotonic revision retained through every reset could close this finding. The document does not expressly extend that invariant through destructive reset, so an implementer cannot tell whether record deletion/recreation is allowed. Successful reset acknowledgement alone does not settle old writers.

**Bounded correction.** State that reset must atomically establish a non-reused writer boundary and that every save and completion checks it. Either preserve a strictly increasing, non-reused revision through reset or use a store generation plus revision; another enforceable exclusion scheme is also acceptable. Define rejection/reconciliation of old tabs and queued work, keep their intent separately available for explicit review, and retain the prior recovery state if reset fails. Ensure purchased-snapshot clearing follows the same ordinary guarded-write invariant if it can retire or recreate storage. This is a local frontend/storage contract, not a request to choose an implementation stack or invent a service capability.

**Evidence and basis.** The frozen review profile's **Work is discarded, removed, finalized or replaced while writes remain queued** trace and `knowledge/state-and-recovery.md`, **Replacement and stale writers**, require an enforceable retirement boundary. **Save snapshots and completion** also distinguishes snapshot acknowledgement from an acknowledgement belonging to an invalidated store generation. This is a bounded document omission; no data loss was reproduced.

## Open owner contracts, separate from defects

The draft correctly blocks capabilities that lack supplied owner evidence. The following remain open inputs rather than additional reported defects:

- **Backend commerce owner:** versioned catalog, variant/quantity eligibility, authoritative quote fields and charges, freshness/expiry, safe quote-read semantics, guest scope, checkout deduplication/retention, lookup, finality, and reconciliation. R1 adds the ordering/conflicting-evidence question to this existing gate.
- **Hosted-checkout integration owner:** actual provider handoff, trusted URL rules, return behavior, accessibility, and cancellation facts. No provider or endpoint is selected.
- **Studio/catalog owner:** real products, accurate variant media and alternatives, rights and creator records, taxonomy/search semantics, brand and charge/legal copy. Gallery illustration fixtures are explicitly prohibited as product photos.
- **Frontend owner:** actual font package/notices, supported browsers, atomic storage implementation and reset policy, implementation and service verification. R2 requires a local behavior decision before that verification.

No stock reservation, tax rule, successful order, duplicate-payment guarantee, support channel, or working backend was inferred.
