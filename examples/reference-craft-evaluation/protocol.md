# A–D implementation: preparation and review rerun protocol

Frozen before dispatch, 2026-10-20. This is a qualitative document trial, not an effectiveness benchmark, a product implementation or a usability result. Interface Atlas is independent of Twohearts.

## Inputs and scope

Rerun the unchanged consumer-app, storefront and bilingual-service briefs in examples/p0-evaluation. Preserve their raw bytes. Historical workflow/revision phrases are superseded only by the dispatch wrapper, which points to the current frozen preparation skill and selectively relevant dependencies; product requirements stay unchanged. The current two skill entry files are unchanged. Knowledge/routing/provenance A–D are the evaluated implementation, identified by a frozen per-file manifest of their uncommitted bytes.

Generators start in fresh contexts with the brief, the minimal reader/output wrapper, AGENTS.md and the preparation entry. They receive no old generated designs, trial findings, evaluation rubric, research notes, practical-lessons index, review draft packet or other generator's output. Selective reading may use the knowledge router, relevant guide sections/credits, catalog/candidate READMEs, selected theme rules/provenance/optional motion and the project template. No upstream skill, external web, code binary, installer, runtime implementation or adapter is a trial input.

## Procedure

1. Freeze the implementation sources and brief bytes before dispatch; record their hashes. Use the same immutable snapshot for all three cases. Keep exact dispatch wrappers and reader helper.
2. Every content read uses the sequential logged helper. It records exact source and returned bytes/hashes, selector, purpose, sequence and time before output. Metadata-only identities are separate. Output truncation is recorded, not assumed away. Returned bytes indicate emitted content, not comprehension, billing or model tokens.
3. Generators write isolated first-draft.md, identical design.md and a requirement-to-heading evaluation.md. Preserve first drafts and original briefs. Do not supply expected answers or route a generator to the newly added chapter by name.
4. Freeze first-draft hashes at handoff. Independently invoke the opt-in review skill in fresh context against each brief and first draft, with no author self-evaluation, historical findings or anticipated defects. Reviews write separate reports and cannot alter input drafts. Reuse legitimately relevant frozen guide sections.
5. Root reads each complete first draft and review and checks requirements/counterevidence. Treat reviewer findings as candidates, not ground truth. Record accepted defects, open dependencies, rejected findings, misses, bounded corrections and evidence limits. Preserve review reports and corrections separately. Later design.md corrections never replace first-draft.md.

## Criteria

Continue the existing requirements: truthful brief scope; explicit theme selection/adaptations; exact light/dark/system values, typography and geometry; task/content/navigation hierarchy; ownership, durable acknowledgement, interruption/re-entry and failure; conditional forms/remote outcomes; keyboard/focus, responsive, reduced motion and bilingual behavior as relevant; self-contained handoff; meaningful validation plans; creators/pins/terms and evidence honesty. Check that mandatory features are not silently removed to avoid a hard transition.

New-method questions: Is A selected only for an unresolved theme/reference decision? Are comparisons task/content/state equivalent without fabricated user scores? Where B is relevant, are planned component roles/state mappings concrete without pretending source code exists? Does C resolve the chosen motion/static policy without automatic library selection? Are D's historical lessons absent from normal generation context? Are full licenses/unused ledgers/adapters avoided unless genuinely needed? These are task-specific judgments, not text/heading matches.

For stateful paths, inspect stale writers after retirement, acknowledgements after newer edits, same-action observation ordering and unknown outcomes under actual capability gates. For bilingual asynchronous UI, inspect obsolete language results and self-contained focus values. Those probes are evaluator questions, not generator instructions. Document-covered rules do not prove transactions or interactions work.

## Focused reference probe

The three regression briefs have no external reference; they cannot establish the external-intake part of A. A separately identified synthetic reference probe uses an existing explicit theme and a small supplied visual reference with internal inconsistency and unresolved terms. Ask for a bounded design revision; provide no expected answer. Check reference admission/claims, preservation of project choice, conditional reading, bounded output and rights handling. The fixture is authored after studying A, so this is a directed capability probe, not held-out generalization. It supplies no licensed real asset or upstream executable code.

## Reporting limits

Report first-pass decisions and supported corrections, capability/input gates, selected versus skipped guidance, content reads/returned bytes and remaining checks. Prior trials had different agents, selected themes, wording and inputs; this rerun cannot isolate causal effects or establish accuracy rates, speed, token/billing savings, production usability or accessibility conformance. No browser/storage/assistive-technology/service/user test is implied. Full license files are distribution evidence, not default invocation reads. New skills/adapters are outside this implementation scope.
