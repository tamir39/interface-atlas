# Frontend and UI/UX skill research

Status: research and adaptation proposal for review, inspected **2026-10-17**. Original comparison and recommendations by **Tamir (Phi Vuong Tuong Tam), with Codex AI assistance**. No skill, template, theme, runtime or installation is implemented by this report.

**Recommendation:** strengthen Atlas's existing preparation workflow, then add one opt-in design review workflow. General UI/UX belongs in both: user goals, task flows, information hierarchy, responsive composition, typography, color, writing and usability evidence. Accessibility and Agent Experience should be selectively loaded review/design profiles, rather than mandatory skill bundles for every frontend task.

This is a bounded comparison of **23 shortlisted skill entries plus two optional Intent sibling entries**, **five command profiles within Impeccable**, and **two primary guidance references**. Six shortlisted entries are owners within the better-interface family; they are not six unrelated review products. Candidates were selected for fit with Atlas's [existing roadmap](../examples/coverage-evaluation/skills-roadmap.md), [P0 trial findings](../examples/p0-evaluation/review-findings.md), and the user's request for general UI/UX. This is not an exhaustive market survey or an effectiveness benchmark.

## Reading cost: what was measured

Entry bytes are pinned UTF-8 file sizes, including front matter and code. Words are non-whitespace runs. **Neither is a token count, price, latency or quality score.** Local source files were inspected as text; no upstream installers, search engines, validators, persona generators or runtimes were executed.

The comparison separates the entry, explicitly required fixed references, conditional branches, and variable project/tool output. A linked reference is not automatically a required read. A database read by a search engine is not automatically model context. License/README evidence is research overhead and is excluded from invocation totals.

Skill metadata is visible before the complete instructions are loaded, so many overlapping descriptions can also add discovery overhead. Short, precise routing and conditional references fit Atlas's cost goal. This follows [OpenAI's activation description](https://developers.openai.com/plugins/concepts/skills) and its [guidance on selective loading](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra); it does not establish how many tokens this particular session consumed.

## What is useful, and what needs adaptation

**Preparation:** ibelick's [create-design-md](https://github.com/ibelick/ui-skills/blob/f18d13077d6e3841821ea0a36526c0fd44a570b5/skills/create-design-md/SKILL.md) is strong at identifying governing design evidence and refusing invented exact tokens. Its required live CLI specification is an unmeasured dependency. Google's [design-md](https://github.com/google-labs-code/stitch-skills/blob/0337446dadde6f8c94210444e2aa9d546126480f/plugins/stitch-utilities/skills/design-md/SKILL.md) starts from existing Stitch screens; [extract-design-md](https://github.com/google-labs-code/stitch-skills/blob/0337446dadde6f8c94210444e2aa9d546126480f/plugins/stitch-design/skills/extract-design-md/SKILL.md) starts from source code. Neither replaces Atlas's brief-to-theme-to-product-contract workflow. Adapt an optional existing-design intake that preserves observed values and uncertainty; avoid automatically consolidating similar colors or inferring product intent from repetition. Impeccable's [document](https://github.com/pbakaus/impeccable/blob/6af45ac9a5eb8792f033d3242f52e99812fd91fa/.agents/skills/impeccable/reference/document.md) offers a useful scan/seed distinction; Atlas should retain its own document contract.

**Review:** [improve-ui](https://github.com/ibelick/ui-skills/blob/f18d13077d6e3841821ea0a36526c0fd44a570b5/skills/improve-ui/SKILL.md) has a strong contract-to-surface-to-correction evidence pattern. Its default scope excludes accessibility and behavior, and limits visual inspection; Atlas must explicitly include the requested flow, browser and accessibility evidence. [Impeccable critique](https://github.com/pbakaus/impeccable/blob/6af45ac9a5eb8792f033d3242f52e99812fd91fa/.agents/skills/impeccable/reference/critique.md) covers broader design judgment but adds substantial reading and runtime orchestration. [Vercel's rules](https://github.com/vercel-labs/web-interface-guidelines/blob/434b7f91364665f2f733b310ec54809bf8f37937/command.md) and ibelick's small checklists are useful preflights. A good Atlas finding needs a concrete failure, affected task, supporting evidence and a bounded correction, with source/heuristic/runtime evidence distinguished.

**General UI/UX:** [Jakub Krehel's family](https://github.com/jakubkrehel/skills/blob/4c66b1fa86e9ab70187b43d7da9b6fdb29f2ef63/skills/better-interface/SKILL.md) provides the strongest inspected domain coverage for layout, typography, colors, writing, accessibility and polish. Use its named ownership and relevant recipes without requiring every domain on every invocation. [Intent Journey](https://github.com/ghaida/intent/blob/3fc38dff381ce0e4dec8f52c97c3e37abd95e10e/skills/journey/SKILL.md) contributes task sequences, decisions, interruption and return. [Anthropic frontend-design](https://github.com/anthropics/skills/blob/dbd4588f9e1033efb41dad4bef2f7947c8993d44/skills/frontend-design/SKILL.md) is an optional creative-direction input; aesthetic warnings remain heuristics that must yield to a legitimate brand/theme choice. [UI/UX Pro Max](https://github.com/nextlevelbuilder/ui-ux-pro-max-skill/blob/56ea9cf174ed86786187daa9de0e6247cb0747e4/.claude/skills/ui-ux-pro-max/SKILL.md) can supply optional pattern/stack search. Its 3,093,030-byte source-data inventory is not a claim that the agent reads 3 MB; query output is variable, and matches still need product-fit and provenance checks.

**Research evidence:** [UX Researcher & Designer](https://github.com/alirezarezvani/claude-skills/blob/19392f7a08264ed00486a251f5b2098321771f94/product-team/skills/ux-researcher-designer/SKILL.md) offers useful journey, usability-task and synthesis methods when real inputs exist. Its [persona generator](https://github.com/alirezarezvani/claude-skills/blob/19392f7a08264ed00486a251f5b2098321771f94/product-team/skills/ux-researcher-designer/scripts/persona_generator.py) CLI always calls bundled sample-data creation and inserts a sample quote; its prepared-JSON instructions are not wired into CLI input. Do not use that output as interview evidence. A library method accepting caller data is a different, unvalidated integration. Adapt the prose methods selectively; exclude synthetic persona execution and unsupported confidence/priority formulas from evidence claims.

**Agent Experience:** [Mohit Aggarwal's skill](https://github.com/mohitagw15856/pm-claude-skills/blob/921e015321cdcf7c48ad85f40eeaf5ba68c89433/skills/human-in-the-loop-design/SKILL.md) is a compact approval-design source; [Burhan Sebin's](https://github.com/seb1n/awesome-ai-agent-skills/blob/75865a5d037a4cdaa7f409a4ec14ab9b0292920b/agent-engineering/human-in-the-loop/SKILL.md) adds exact payload/diff, effects, evidence, uncertainty and failure conditions. Both have useful but narrower scope than a whole agent interface. The broad [AI-First SaaS package](https://github.com/marketingskills/ai-first-saas-interface/blob/42c76d040956924e3a72f25a98277f04342338d8/SKILL.md) is comparison-only because no explicit reuse grant was identified in its inspected entry/support files. Do not copy, translate or repackage it into Atlas. [Microsoft HAX](https://www.microsoft.com/en-us/haxtoolkit/ai-guidelines/) and [Google PAIR](https://pair.withgoogle.com/guidebook/) are primary guidance references, not installable skills; use linked concepts to inform independently written Atlas questions without bundling their pages/assets.

The phrase “agent experience” also covers model-facing SDK/tool onboarding. That is a different subject from this request's human-facing progress, decisions, steering and recovery. Backend agent builders and framework integrations are not substitutes for a human-agent design lens.

## Proposed Atlas shape, before implementation

Keep **two public workflow entry points** as the initial proposal: the existing `prepare-frontend-design`, and a future opt-in `review-frontend-design`. General UI/UX should be a first-class preparation/review mode, not a polish appendix. A third general-design or flow skill is justified only if repeated use shows a distinct input/output contract and lower omissions or reading scope.

| Mode or selective profile | Inputs and intended output | Recommended adaptation |
| --- | --- | --- |
| General UI/UX preparation | Brief and available user/content evidence → goals, information structure, task/state map, responsive composition and design rationale | Intent journey reasoning; selected research methods; better-layout/writing/type/color references |
| Project design handoff | Resolved design decisions + chosen theme + actual constraints → self-contained project design.md with source/adaptation/unknown/evidence boundaries | Existing Atlas preparation, source-aware extraction and document methods; no compulsory Google/Impeccable schema |
| Design review | Brief + project design.md + supplied implementation/evidence → prioritized issues and review coverage | improve-ui evidence discipline, selected critique/walkthrough methods, relevant Atlas knowledge |
| Accessibility/responsive profile | Named components, tasks and supported contexts → checks performed, failures, applicability and remaining browser/AT checks | Selected accessibility/layout recipes and focused preflights; primary standards retain authority |
| Agent Experience profile | Actual agent capabilities/actions/contracts → expectation, proposal, progress, intervention and recovery decisions | Licensed approval-design concepts plus independently authored lifecycle questions supported by HAX/PAIR and existing Atlas knowledge |
| Optional existing-project/stack adapter | Existing source/screens or a concrete stack → observed inventory and stack mapping | Google extraction or optional Pro Max lookup, loaded only when needed |

Theme-first browsing remains useful for Atlas's catalog. The design reasoning should begin with the project's users, tasks, content and constraints, then adapt the selected theme. A palette or style match does not settle a flow, state owner or uncertain outcome.

The general UI/UX layer should cover: problem/evidence strength; primary tasks; information architecture and content order; journey and alternative states; hierarchy, grouping and density; typography; semantic color and both appearances; responsive/input/RTL behavior; UX writing; optional motion/effects; accessibility; and validation questions. Separate observations, hypotheses and decisions. Do not invent interviews, business rules, backend guarantees or success metrics.

## Prioritized adaptation plan

1. **Preparation and general UI/UX first:** add a small selective route from the existing preparation entry to task/flow, layout, writing, type/color and the relevant P0 chapters. Reuse existing Atlas knowledge instead of importing another complete design system.
2. **One opt-in review workflow:** support artifact review before implementation, with optional source/browser modes. Consolidate root causes and report missing evidence. A review request alone should not trigger implementation.
3. **Accessibility/responsive profile:** keep quick source triage distinct from comprehensive keyboard, zoom/reflow, assistive-technology and appearance checks. Use actual evidence to state what passed.
4. **Agent Experience extension:** extend the existing chapter rather than create a parallel authority model. Research/project contracts must bind approval to the actual proposal, and distinguish attention, execution, connection, pending command and uncertain result. Test changed proposals and lost acknowledgements in a fresh operations brief before asserting coverage.
5. **Optional retrieval/adapters later:** assess Pro Max or Stitch integration only when a real source/stack need justifies their tools and output formats. No new package is necessary for a plain Markdown design-preparation workflow.

Before a future skill change, preserve source notices and modification records, define precise triggers/output contracts, and compare against the existing trials plus an unseen brief. Measure selected reads, omissions, contradictions and unsupported claims. Known consumer/storefront/service briefs are regression cases, not held-out proof of improved outcomes. Browser, assistive-technology, usability-study and real-service evidence remain separate.
